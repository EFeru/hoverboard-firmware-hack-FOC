# Боковая плата как DroneCAN-узел (AP_Periph): что проверено и как делать

Продолжение [`docs/can-dronecan-sideboard.md`](can-dronecan-sideboard.md).
Здесь — ответы на конкретные вопросы: работает ли CAN на PB8/PB9 вместе с
загрузчиком, что мешает, и как собрать прошивку на GitHub.

Готовые файлы для сборки — в [`docs/ap-periph/`](ap-periph/README.md).

---

## 1. Главный ответ: CAN на PB8/PB9 и загрузчик

**Да, работает — и загрузчик тоже.** Доказательство найдено в самом ArduPilot:

* CMSIS-заголовок `stm32f103xb.h`:
  `AFIO_MAPR_CAN_REMAP_REMAP2` → **CANRX = PB8, CANTX = PB9**
  (для сравнения: `AFIO_MAPR_CAN_REMAP_REMAP1` = PA11/PA12);
* в ArduPilot есть готовая плата-аналог — **ZubaxGNSS** (STM32F105, тоже F1,
  тоже AP_Periph), и ремап ставится в **двух** местах:
  * `Tools/AP_Periph/AP_Periph.cpp` (приложение),
  * `Tools/AP_Bootloader/AP_Bootloader.cpp` (загрузчик).

```c
#ifdef HAL_BOARD_AP_PERIPH_ZUBAXGNSS
    uint32_t mapr = AFIO->MAPR;
    mapr &= ~AFIO_MAPR_SWJ_CFG;
    mapr |= AFIO_MAPR_SWJ_CFG_JTAGDISABLE;
    AFIO->MAPR = mapr | AFIO_MAPR_CAN_REMAP_REMAP2 | AFIO_MAPR_SPI3_REMAP;
#endif
```

Значит, схема «CAN на разъёмах LED-плат + обновление прошивки по CAN» — рабочая,
просто у Zubax это сделано для их платы, а нам нужно то же для своей (см. патч).

Что при этом **обязательно** учитывать:

| Что | Почему |
|---|---|
| Снять транзисторы (или базовые резисторы) LED2/LED3 | PB9/PB8 идут на базу SOT-23 через 1 кОм. База — это диод на землю: на приёме (PB8) линия зажмётся на ~0.7 В и CAN **не заработает**; на передаче (PB9) транзистор будет мигать светодиодом от каждого кадра |
| Патч и в приложение, и в загрузчик | ремап ставится программно; без патча загрузчик останется на PA11/PA12 и обновление по CAN не заработает |
| LED2 (зелёный) и LED3 (жёлтый) теряются | это цена за удобную пайку; LED1, LED4, LED5 остаются |

**Альтернатива без ремапа — PA11/PA12** (заводские пины CAN): патч для CAN не
нужен вообще (штатный `f103-periph` уже так объявлен), загрузчик работает
«из коробки», все 5 светодиодов целы. Минус — два провода придётся припаять к
выводам MCU (LQFP48, шаг 0.5 мм).

| | PB8/PB9 (ремап) | PA11/PA12 (без ремапа) |
|---|---|---|
| Пайка | к разъёмам LED-плат J3/J4 | к выводам MCU |
| Демонтаж | 2 транзистора/резистора | не нужен |
| Светодиоды | −LED2, −LED3 | все целы |
| Патч прошивки | нужен (app + bootloader) | не нужен |
| Загрузчик по CAN | работает (после патча) | работает штатно |

## 2. Что мешает сильнее всего: кварца на плате нет

Прошивка EFeru для боковой платы тактируется **от внутреннего HSI**:

```c
RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_HSI;
RCC_OscInitStruct.PLL.PLLSource  = RCC_PLLSOURCE_HSI_DIV2;
RCC_OscInitStruct.PLL.PLLMUL     = RCC_PLL_MUL16;   // 8 МГц / 2 * 16 = 64 МГц
```

В ArduPilot/ChibiOS для F1 жёстко требуется HSE — есть только одна HSI-ветка
(`AP_IOMCU_BOOTLOADER`, HSI/2 × 6 = 24 МГц) и выбор конфигурации по
`STM32_HSECLK`. Без кварца `STM32_HSE_ENABLED TRUE` → ChibiOS ждёт `HSERDY` и
инициализация не проходит.

Решение (уже в патче `docs/ap-periph/ardupilot-sideboard.patch`):

```c
#if defined(HAL_BOARD_HOVERBOARD_SB)
// Hoverboard sideboard (no crystal): HSI/2 * 16 = 64 MHz
#define STM32_PLLSRC        STM32_PLLSRC_HSI
#define STM32_PLLMUL_VALUE  16
#define STM32_PPRE1         STM32_PPRE1_DIV2
#define STM32_PPRE2         STM32_PPRE2_DIV1
#define STM32_ADCPRE        STM32_ADCPRE_DIV8
#define STM32_HPRE          STM32_HPRE_DIV1
...
```
(значение 16 корректно: ChibiOS считает `(STM32_PLLMUL_VALUE - 2) << 18`, а поле
регистра для ×16 — это `0b1110` = 14.)

⚠️ **Риск точности HSI для CAN.** HSI на F103 калиброван до ±1 %, CAN 2.0 надёжно
работает при расхождении клоков около ±0.5 %. На коротком шлейфе (несколько
десятков сантиметров) это обычно проходит, но не гарантируется. Если появятся
ошибки шины — припаять кварц 8 МГц к PD0/PD1 (на GD32F130 — PF0/PF1) и вернуть
HSE-ветку в патче.

## 3. Флеш: AP_Periph для F103 — это ~100 КБ

Измерено на официальном сервере сборок (`f103-GPS`, стабильная ветка):

| Файл | Размер |
|---|---|
| `AP_Periph.bin` | **102 808 Б ≈ 100 КБ** |
| загрузчик + параметры (резерв) | 25 КБ |

Итого нужно **128 КБ** флеша — ровно как в штатном `f103-periph` («assume the
128k flash part»).

* Если чип на вашей плате — настоящий STM32F103C8T6, у него почти всегда
  физически **128 КБ** (ST гарантирует только 64 КБ, но кремний полный) → влезет,
  но впритык.
* Если это **GD32F103C8T6** (клон, как в STM-репозитории и написано) — там честные
  **64 КБ** → AP_Periph **не влезет**. Тогда остаётся UART-путь или маленькая своя
  прошивка.
* Проверка — при первом запуске сборки: если `AP_Periph.bin` больше ~103 КБ или
  прошивка не стартует после заливки, вопрос закрыт.

## 4. Что узел на AP_Periph умеет (и чего не умеет)

Проверено по исходникам ArduPilot:

| Функция | Как | Готовность |
|---|---|---|
| **5 управляемых выводов** (ключи LED1…LED5) | FC: `RELAYx_FUNCTION = 10…25` (DroneCAN hardpoint 0…15) → узел переключает свой пин (`AP_Relay`, `Tools/AP_Periph/relay.cpp`) | ✔ штатно |
| Команды из миссии/MAVLink/Lua | `MAV_CMD_DO_SET_RELAY` → тот же hardpoint | ✔ штатно |
| **Индикация светодиодами** | `uavcan.equipment.indication.LightsCommand` (AP рассылает состояние: батарея, arm, ошибки) | ✔ механизм есть, но нужен свой маппинг «цвет → 2–3 светодиода» |
| **Кнопки/концевики** | `ardupilot.indication.Button` (в AP обрабатывается в первую очередь как safety button) | ⚠️ частично |
| **Обновление прошивки по CAN** | загрузчик + `FLASH_BOOTLOADER` | ✔ (при ремапе — после патча) |
| Авто-выдача node ID, параметры в flash | штатно | ✔ |
| **Сырьё IMU** (`ahrs.RawIMU`) | публикуется, но **ArduPilot его не потребляет** (только PX4) | ✘ для AP |
| Готовые углы/наклон | такого сообщения, которое AP потребляет, нет | ✘ |

Отсюда практический вывод для ваших задач: **AP_Periph-узел на боковой плате —
это, прежде всего, узел ввода-вывода (свет, реле, кнопки)**, а не датчик наклона.

## 5. Трафик: при 10–50 Гц CAN вообще не проблема

Ваша интуиция верна, и цифры это подтверждают (шина 500 кбит/с, полная загрузка
≈ 33 кБ/с):

| Поток | Кадров/с | Загрузка |
|---|---|---|
| Стандартный `RawIMU` (61 Б) на **10 Гц** | 90 | ≈ **2 %** |
| `RawIMU` на **50 Гц** | 450 | ≈ 11 % |
| Компактный кадр 18 Б на **10 Гц** | 30 | < 1 % |
| 5 реле + 4 кнопки (события) | ≪ 10 | ~0 % |

То есть «беречь трафик» для датчика подвески/манипулятора — задача уже решённая:
10–50 Гц по CAN это доли процента. Проблема была только при 200–1000 Гц.

## 6. Как я предлагаю разложить задачи (важное разделение)

Ключевой момент: **AP_Periph — это фиксированное приложение**. Если узел бежит
под AP_Periph, он не может «сам посчитать наклон и дёрнуть реле» — для этого
нужна своя прошивка. Отсюда три разных сценария:

| Сценарий | Прошивка узла | Что получаете | Когда выбирать |
|---|---|---|---|
| **A. IO-узел** | AP_Periph (готовая) | 5 управляемых выводов, свет, кнопки; обновление по CAN; всё стандартными средствами FC | свет/реле на косилке, концевики — «минимальная доработка» в чистом виде |
| **B. Узел наклона** | своя прошивка (sideboard-hack + логика) | узел сам считает наклон/крен и **замыкает один из своих 5 ключей** → это «сухой контакт» на вход FC (кнопка/GPIO) или на вход ESP32; свет/реле — по своим правилам | переворот косилки, ход подвески, положение плеча |
| **C. Мост** | своя прошивка + ESP32 | поток углов в UART/MAVLink/Wi-Fi → ArduPilot (`ODOMETRY`/`VISION`) или ROS2 (`sensor_msgs/Imu`) | когда нужен именно угол числом в автопилот/ROS2 |

Почему для переворота я советую **B**, а не A: в ArduPilot наклон по DroneCAN
не доедет (нет потребителя сообщения), а «сухой контакт» — универсален: его
понимает и ArduPilot (вход кнопки/GPIO + `BTNx_FUNCTION`), и ESP32, и обычное
реле. Это же и есть «минимальная доработка, максимальная польза».

## 7. Организация кода: нужен ли новый репозиторий и новая сессия

**Новый репозиторий — да, полезен.** AP_Periph-периферия — отдельный продукт со
своим CI, и держать её в репозитории прошивки гироскутера неудобно.

**Новая сессия — не нужна.** Я не «забываю» в рамках этой сессии, а всё важное
лежит в файлах репозитория:

* `docs/sideboards.md` — железо, распиновка, отладочный режим;
* `docs/can-dronecan-sideboard.md` — CAN/DroneCAN, трафик, ESP32-мост;
* **`docs/ap-periph-sideboard.md`** (этот файл) — решение и план;
* **`docs/ap-periph/`** — готовые файлы: `hwdef.dat`, `hwdef-bl.dat`, патч
  ArduPilot и workflow сборки.

Даже если открыть новый чат — новая сессия поднимет контекст из этих файлов.

⚠️ Ограничение: я не могу пушить в **другой** репозиторий — моя работа привязана
к этой ветке этого репозитория. Поэтому порядок такой: я готовлю и проверяю файлы
здесь, вы создаёте новый репозиторий (например
`marshalab/hoverboard-sideboard-AP_Periph`), копируете в него содержимое
`docs/ap-periph/` — и GitHub Actions собирает вам готовый `.bin`/`.apj` + загрузчик.

## 8. Пошаговый план

1. **Собрать без железа.** Создать репозиторий по `docs/ap-periph/README.md`,
   запустить workflow → получить `AP_Periph.bin`, `AP_Periph.apj` и `*_bl.bin`.
   По логу сразу видно размер: влезает или нет.
2. **Определиться с пинами CAN.** PA11/PA12 (пайка к MCU, без патча) или
   PB8/PB9 (пайка к J3/J4 + снять 2 транзистора + раскомментировать ремап в патче).
3. **Пропаять трасивер** (SN65HVD230, 3.3 В — питание с платы), 120 Ω на концах.
4. **Залить через ST-Link:** загрузчик по `0x08000000`, приложение по
   `0x08006400` (25 КБ резерва).
5. **Проверить в DroneCAN GUI / Mission Planner**, задать параметры реле и
   node ID; проверить индикацию и обновление прошивки по CAN.
6. **Второй шаг (по желанию):** своя прошивка на GD-платах — датчик угла с
   «сухим контактом» на выходе (сценарий B), и/или добавить IMU в AP_Periph-узел
   (`define AP_PERIPH_IMU_ENABLED 1`) для PX4-совместимости.

---

## 9. Что осталось выяснить на практике

* Реальный размер флеша вашего чипа (128 КБ или 64 КБ).
* Стабильность CAN на HSI (без кварца) — проверить под нагрузкой.
* Маппинг параметров реле на узле (`RELAYx_FUNCTION` / `RELAYx_PIN`) — уточнить
  при первом подключении к DroneCAN GUI.
* Нужен ли `LED4/AUX3` дублирующий выход (в штатной прошивке он повторяет LED4) —
  если да, в hwdef добавить его как ещё один GPIO.
