# CAN / DroneCAN на боковых платах: что реально возможно

Разбор вопроса «можно ли подключить CAN-трасивер к боковой плате, стоит ли гнать
сырьё IMU через DroneCAN, и что из этого нужно ArduPilot / ROS2».

Источники: даташиты из репозиториев (`docs/stm32f103c8-Datasheet.pdf`,
`docs/GD32F130xx-Datasheet_Rev3.3.pdf`), исходники ArduPilot (AP_Periph, AP_Relay,
AP_DroneCAN), DSDL DroneCAN, документация ESP-IDF.

---

## 1. Главный вывод в одну строку

| Плата | CAN-контроллер | Можно ли подключить трасивер |
|---|---|---|
| **STM32F103C8T6** (STM-версия) | **есть** (1× bxCAN) | да: **PA11 = CAN_RX, PA12 = CAN_TX** (на микросхеме свободны, на разъёмы не выведены) |
| **GD32F130C6T6** (GD-версия) | **нет** | нет: CAN-периферии в кристалле не существует |

---

## 2. Почему на GD32F130 нет CAN — доказательства

1. **Карта памяти** (даташит, §2.4, табл. 2-2): перечислены USART0/USART1, SPI0/SPI1,
   I2C0/I2C1, TIMER0..2/13..16, ADC, DMA, RTC, PMU, FWDGT/WWDGT, EXTI, SYSCFG —
   **блока CAN в адресном пространстве нет**.
2. **Оглавление и функциональное описание** (§3): разделы про ADC, DMA, GPIO,
   таймеры, RTC, I2C, SPI, USART, Debug — **раздела CAN нет**.
3. **Все таблицы выводов** (LQFP64 / LQFP48 / LQFP32 / QFN32 / QFN28 / TSSOP20):
   ни у одного вывода нет альтернативной функции CAN_RX/CAN_TX.
   PA11/PA12 (там, где у STM32F103 живёт CAN) — это `USART0_CTS/RTS`,
   `TIMER0_CH3/ETI`, `EVENTOUT`.

Значит, для GD-платы аппаратный CAN невозможен. Теоретический обходной путь —
внешний контроллер **MCP2515 по SPI0** (SCK/MISO/MOSI = PA5/PA6/PA7, CS и INT —
например PA1/PC15/PB10), но эти выводы на разъёмы не выведены, паять придётся к
ногам LQFP48 с шагом 0.5 мм. Как рабочий вариант это не рассматриваем.

## 3. STM32F103C8T6: CAN есть, но пины надо распаять

* Даташит: «…up to two I2Cs and SPIs, three USARTs, an USB and a CAN»;
  Table 2 для STM32F103Cx: **CAN = 1**; на блок-диаграмме CAN_TX/CAN_RX
  мультиплексированы с USBDM/USBDP.
* Выводы по умолчанию: **PA11 (CAN_RX) и PA12 (CAN_TX)**. USB на боковой плате
  не используется, конфликтов нет.
* Альтернативная (remap) пара — **PB8/PB9**, но это LED3/LED2 на плате (ключи
  светодиодов) → заняты.
* В прошивке боковой платы PA11/PA12 не упоминаются (проверено по `Inc/defines.h`
  и `Inc/main.h` обоих репозиториев) — то есть на плате они свободны,
  но на 4-пиновый кабель, LED-разъёмы и AUX-гребёнку они не выведены.
  Нужна пайка тонким проводом к выводам MCU.

### Обвязка трасивера

```
Боковая плата (STM-версия)                Трансивер 3.3 В (SN65HVD230 / TJA1051T/3)
  PA12 (CAN_TX)  ─────────────────────►  TXD (D)
  PA11 (CAN_RX)  ◄─────────────────────  RXD (R)
  3V3 (AMS1117)  ─────────────────────►  VCC   (Rs/slope → GND = high-speed)
  GND            ─────────────────────►  GND
                                          CANH / CANL ──► шина (+120 Ω на концах)
```

* 5-вольтовые TJA1050/MCP2551 — только с согласованием уровня по линии RX
  (PA11/PA12 у STM32F103 — 5 В-толерантные, но вход трасивера лучше кормить
  3.3 В-логикой).
* Землю трасивера и платы соединять обязательно; CAN-шина — витая пара,
  терминаторы 120 Ω на двух концах.

## 4. Что ArduPilot уже умеет по DroneCAN

### 4.1. Готовая прошивка узла — AP_Periph

`Tools/AP_Periph` — «периферийная» прошивка ArduPilot: превращает плату в
DroneCAN-узел. README прямо говорит: поддерживаются все MCU ArduPilot, включая
**STM32F1xx**, 60+ готовых сборок; есть автоматическая выдача node ID,
bootloader, хранение параметров во flash и **обновление прошивки по CAN**.

Более того, существует готовый hwdef **`libraries/AP_HAL_ChibiOS/hwdef/f103-periph`**,
где уже прописано:

```
PA11 CAN_RX CAN
PA12 CAN_TX CAN
PB6  I2C1_SCL I2C1        ← это же пины MPU-6050 на боковой плате
PB7  I2C1_SDA I2C1
PA9  USART1_TX / PA10 USART1_RX
define HAL_CAN_POOL_SIZE 2500
FLASH_RESERVE_START_KB 25   (bootloader + параметры)
```

То есть эталонный hwdef почти совпадает с распиновкой боковой платы: остаётся
переписать светодиодные ключи, входы фото-датчиков и добавить IMU.

### 4.2. «Просто управляемые выводы» — это штатная функция DroneCAN

| Хочу | Механизм в ArduPilot | Проверено по коду |
|---|---|---|
| Управлять ключами/реле с полётного контроллера | FC шлёт `uavcan.equipment.hardpoint.Command`; параметр `RELAYx_FUNCTION = 10…25` = DroneCAN hardpoint 0…15; узел вызывает `relay.set()` на своих пинах | `libraries/AP_Relay/AP_Relay.cpp` (`msg.hardpoint_id = index`, `relay_hardpoint.broadcast(msg)`), `AP_Relay_Params.h` (`DroneCAN_HARDPOINT_0…15 = 10…25`), `Tools/AP_Periph/relay.cpp` |
| Индикация светодиодами | FC рассылает `uavcan.equipment.indication.LightsCommand` (цвет = состояние батареи/arm/ошибок) | `libraries/AP_Notify/DroneCAN_RGB_LED.cpp` (публикация), `Tools/AP_Periph/can.cpp` (приём и раскладка цветов) |
| Кнопки/концевики с узла в автопилот | `ardupilot.indication.Button` (в т.ч. safety button) | `libraries/AP_DroneCAN/AP_DroneCAN.cpp` → `handle_button()` |

То есть «5 ключей платы» из миссии/MAVLink/Lua — это не самоделка, а штатная
схема. На стороне FC: `RELAYx_FUNCTION`, далее обычный `MAV_CMD_DO_SET_RELAY`
или Lua `relay:set()`.

### 4.3. Сырьё IMU через DroneCAN — есть, но не для ArduPilot

* **Отдавать** — можно: `Tools/AP_Periph/imu.cpp` публикует
  `uavcan.equipment.ahrs.RawIMU` (флаг сборки `AP_PERIPH_IMU`, по умолчанию
  выключен). Причём он отправляет не только «последние» значения, но и
  **интегралы** (`get_delta_angle()` / `get_delta_velocity()`).
* **Принимать в ArduPilot — нельзя**: поиск по всему дереву ArduPilot находит
  `RawIMU` только в `Tools/AP_Periph/imu.cpp` и `Tools/scripts/build_options.py`.
  Ни EKF, ни `AP_InertialSensor` это сообщение не потребляют.
* **PX4 — потребляет**: `src/drivers/uavcan/sensors/gyro.cpp`, `accel.cpp`
  (подписка на RawIMU) и `src/drivers/uavcannode/Publishers/RawIMU.hpp`.

Вывод: «сырьё IMU по DroneCAN» — рабочий стандарт, но ведёт он сегодня в
PX4/кастомного потребителя, а не в ArduPilot.

### 4.4. MPU-6050 боковой платы — да, драйвер есть

`AP_InertialSensor_Invensense` умеет не только SPI, но и I2C, а в hwdef это
пишется строкой вида:

```
IMU Invensense I2C:0:0x68 ROTATION_NONE
```

живые примеры: `hwdef/crazyflie2/hwdef.dat` (`IMU Invensense I2C:0:0x69`),
`hwdef/skyviper-journey/hwdef.dat` (`IMU Invensense I2C:1:0x68`).
Адрес MPU-6050 = 0x68, шина I2C0 → PB6/PB7. Технически связка «боковая плата =
DroneCAN-IMU» достижима.

## 5. Сколько трафика съедает сырьё (главная причина не гнать его по CAN)

Расчёт для классического CAN 2.0B, кадр с 8 байтами данных ≈ 111 бит + битстаффинг
(≈10–20 %) ≈ 120–135 бит:

| Режим | Кадров/с при 500 кбит/с | Полезных кБ/с |
|---|---|---|
| 500 кбит/с | ≈ 3700…4100 | ≈ 30…33 |
| 1 Мбит/с | ≈ 7400…8300 | ≈ 60…66 |

Теперь размеры сообщений:

**Своё компактное сообщение** (gyro int16×3 + accel int16×3 + timestamp + счётчик
≈ 18 байт) → 3 кадра DroneCAN на сообщение:

| Частота | Кадров/с | Загрузка шины 500 кбит/с |
|---|---|---|
| 200 Гц | 600 | ≈ 14 % |
| 500 Гц | 1500 | ≈ 36 % |
| 1 кГц | 3000 | ≈ 72 % (впритык, без запаса) |

**Стандартный `uavcan.equipment.ahrs.RawIMU`**: timestamp 7 Б +
integration_interval 4 Б + `float16[3]` gyro 6 Б + `float32[3]` интеграл 12 Б +
`float16[3]` accel 6 Б + `float32[3]` интеграл 12 Б + ковариация (`float16[<=36]`,
обычно 6 значений ≈ 14 Б) ≈ **61–62 байта** → **9 кадров на одно сообщение**:

| Частота | Кадров/с | Загрузка шины 500 кбит/с |
|---|---|---|
| 50 Гц | 450 | ≈ 11 % |
| 200 Гц | 1800 | ≈ 43 % на **ОДИН** датчик |
| 500 Гц | 4500 | ≈ 108 % — не влезает |

Отсюда практика, которую применяет сам ArduPilot: внутри узла считать **интегралы**
на высокой частоте (1 кГц) и публиковать их на 50–200 Гц. Тогда «сырьё» едет
редко и компактно, а разрешение по времени сохраняется.

CAN FD (64 байта в кадре, RawIMU влезает в один кадр) снимает проблему, но
ни GD32F130, ни STM32F103 его не поддерживают — нужен STM32H7/FDCAN.

## 6. UART vs CAN для боковой платы

| | UART (кабель платы) | CAN 2.0 |
|---|---|---|
| Скорость | 115200 по умолчанию, 460800 в прошивке; при 48/72 МГц реально до ≈921.6 кбит/с (≈92 кБ/с) | ≈30–33 кБ/с полезных при 500 кбит/с |
| Топология | точка-точка, по одному проводу на плату | **шина**: десятки узлов на одной витой паре |
| Плюсы | просто, уже есть, максимальная скорость для сырья | арбитраж, CRC, авто node ID, hot-plug, обновление прошивки по шине, готовая экосистема DroneCAN/AP_Periph |
| Минусы | нет шины, нет стандарта сообщений | медленнее, нужен трасивер и своя прошивка |

Один датчик на 1 кГц по UART — 18 кБ/с, то есть ~20 % от 921.6 кбит/с. По CAN при
500 кбит/с тот же поток — уже 72 % шины. **Для сырья UART выигрывает по скорости;
CAN выигрывает по удобству сети и стандартизации.**

## 7. ESP32 как промежуточный узел — оценка идеи

Да, это рабочая и, пожалуй, оптимальная схема, потому что у ESP32 есть всё сразу:

* **TWAI** — встроенный CAN-контроллер (CAN 2.0B, 1 шт.) в ESP32/S2/S3/C3/C6;
  FD не поддерживается. Нужен внешний трасивер: **SN65HVD230** (3.3 В) —
  самый простой вариант; ESP-IDF v6.1: `esp_twai.h`, `twai_new_node_onchip()`,
  `twai_node_enable()`, `fail_retry_cnt = 0` для single-shot.
  ⚠️ По S3 есть противоречивые сообщения сообщества (якобы в поздних партиях
  кристалл без TWAI) — проверяйте конкретный модуль; официальная документация
  Espressif для ESP32-S3 заявляет 1 TWAI-контроллер.
* **UART × 2–3** — можно повесить несколько боковых плат (каждой свой порт).
* **Wi-Fi** — выход в ROS2 (micro-ROS/XRCE-DDS) без проводов.

Что делает такой мост:

```
боковая плата 1 (UART 921600) ─┐
боковая плата 2 (UART)        ─┼─► ESP32 ─┬─► UART MAVLink → ArduPilot (ODOMETRY / VISION / HIGHRES_IMU)
боковая плата N               ─┘  (фильтр,│
                                   fusion) └─► TWAI + SN65HVD230 → DroneCAN (свет/реле/IMU-дайджест)
                                           └─► Wi-Fi → ROS2-топики
```

Ключевое: мост **разгружает** боковую плату от того, что ей не по силам
(4 КБ RAM у GD32F130C6, 20 КБ у STM32F103C8 — там нет места ни micro-ROS, ни
полноценному CAN-стеку с DSDL), и **не грузит CAN сырьём**.

## 8. Подвеска: «IMU на каждое колесо/ось»

CAN делает эту идею практичной: узлы различаются node ID, а не «каждый требует
своего порта», как с UART.

Что реально измеряется и чего ждать:

* **Наклон/ход рычага подвески** — по углам (roll/pitch) относительно рамы:
  6-осевой fusion (Madgwick/Макока) даёт устойчивый наклон, yaw не нужен
  (магнитометра на плате нет, yaw со временем уходит).
* **Удары и вибрации** — акселерометр: полезно для диагностики/аварий.
* **Вертикальный ход** — двойное интегрирование ускорения дрейфует; надёжнее
  измерять ход отдельно (потенциометр, ToF, линейный энкодер), а IMU использовать
  для компенсации гравитации (нужен известный наклон).
* Ставить датчик на **рычаг/ось**, а не на диск колеса: на колесе IMU видит
  вращение (1 об/с = 360 °/с) как помеху.
* Если угол/скорость нужны с высокой частотой — считайте локально на узле
  (или на ESP32) и отдавайте **дайджест**, а не сырьё.

## 9. Итоговая матрица «что выбрать»

| Цель | Сырьё IMU | Управляемые выводы / свет | Как соединять |
|---|---|---|---|
| **ArduPilot-Rover** | не по DroneCAN (нет потребителя): UART→ESP32→MAVLink (ODOMETRY/VISION) либо свой драйвер External AHRS | ✔ DroneCAN: `RELAYx_FUNCTION=10…25`, `LightsCommand`, `Button` (AP_Periph) | 1 шина CAN + AP_Periph-узлы; сырьё — отдельным UART-каналом |
| **PX4** | ✔ DroneCAN RawIMU потребляется штатно | ✔ аналогично (uavcannode/DroneCAN) | CAN-шина |
| **ROS2** | ✔ но проще без CAN: UART/Wi-Fi + `sensor_msgs/Imu` | ✔ relay/GPIO-топики; либо CAN→ROS2-мост | ESP32/RPi как мост |

**Практические выводы:**

1. **GD-платы** для CAN непригодны вообще; как UART-датчики/IO — вполне.
2. **STM-платы** — CAN есть на PA11/PA12, но нужна пайка к MCU; если нужен
   именно CAN-узел, дешевле взять BluePill (STM32F103C8, CAN-пины на гребёнке)
   или ESP32: у BluePill есть официальный AP_Periph-hwdef `f103-periph`.
3. **Сырьё 200 Гц–1 кГц не надо гнать по классическому CAN** — это 40–100 % шины
   на один датчик. Правильно: интегралы/дайджест на 50–200 Гц либо UART.
4. **«Просто управляемые выводы» — лучший сценарий для DroneCAN**: свет и реле
   работают штатными средствами ArduPilot, без своего кода на FC.

## 10. Что можно сделать дальше

1. **hwdef под боковую плату (STM)** для AP_Periph: CAN на PA11/PA12, MPU-6050
   на I2C0 (PB6/PB7), 5 ключей как DroneCAN-реле 0…4, два фото-датчика как GPIO →
   получается готовый `firmware.bin` + загрузчик (обновление по CAN).
2. **Спецификация узла** для ESP32-моста: кадр `start, gyro×3, accel×3, temp,
   io, cmd, CRC` на 200–500 Гц + команды на 5 ключей.
3. **Прозвонка конкретной платы**: убедиться, что PA11/PA12 действительно
   доступны для пайки (на GD-плате смысла нет в принципе).
