# SBSP v1 — протокол «боковая плата → ESP32»

**SBSP** = *SideBoard Sensor Protocol*, вариант прошивки боковой платы
`VARIANT_SENSOR`. Плата перестаёт быть «боковой платой гироскутера» и становится
автономным датчиком положения + узлом ввода/вывода:

* отдаёт **roll и pitch** (на трёх платах — те самые 6 углов: 3 элемента ×
  roll/pitch), плюс сырую угловую скорость gyro Z;
* по команде — расширенный кадр с yaw и сырыми gyro/accel;
* принимает **команды светодиодов** (5 выходов LED1…LED5);
* отдаёт состояние **двух оптических датчиков**;
* частоту потока можно менять по UART: 1, 2, 5, 10, 20, 50, 100, 200 Гц
  (по умолчанию **200 Гц**), настройка **сохраняется в флеш** по флагу `save`;
* **с основной платой гироскутера не взаимодействует вообще** — прошивка не
  содержит ни `SERIAL_FEEDBACK` (кадр от основной платы), ни iBUS/AUX-логики.

Всё, что нужно знать по железу, — в `docs/sideboards.md` (§2, §5): 4-пиновый
кабель (GND, 12–15 В, USART), USART1, 115200 8N1, уровни 3.3 В.

---

## 1. Кадр

```
A5 5A | type | len | payload[len] | CRC-8
 2 B     1 B    1 B     len B        1 B
```

* `A5 5A` — SOF (в этом порядке байт на проводе);
* `len` — длина payload, не больше `SBSP_MAX_PAYLOAD` = 24; кадр длиннее —
  отбрасывается;
* **CRC-8**: полином `0x07`, начальное значение `0x00`, считается по байтам
  `type`, `len` и `payload` (без SOF и без самого CRC).

Пример: `A5 5A 01 0A 07 04 34 12 9C FF 05 00 40 00 1E …` — SOF, DATA, len=10,
payload, CRC.

Накладные расходы кадра — 5 байт.

## 2. Сообщения

| type | имя | направление | len | кому отвечает |
|---|---|---|---|---|
| `0x01` | `DATA` | плата → ESP32 | 10 | — |
| `0x02` | `DATA_EXT` | плата → ESP32 | 22 | — |
| `0x10` | `SET_RATE` | ESP32 → плата | 3 | `ACK` |
| `0x11` | `SET_MODE` | ESP32 → плата | 1 | `ACK` |
| `0x12` | `LED` | ESP32 → плата | 2 | `ACK` |
| `0x13` | `SET_ID` | ESP32 → плата | 1 | `ACK` |
| `0x14` | `SAVE` | ESP32 → плата | 0 | `ACK` |
| `0x15` | `GET_INFO` | ESP32 → плата | 0 | `INFO` |
| `0xE0` | `INFO` | плата → ESP32 | 7 | — |
| `0xE1` | `ACK` | плата → ESP32 | 2 | — |

Многобайтовые поля — **little-endian**.

### 2.1. `DATA` (0x01), 10 байт payload

| Смещение | Поле | Тип | Смысл |
|---|---|---|---|
| 0 | `seq` | u8 | счётчик кадров, растёт на 1 в каждом кадре, переносится через 255 |
| 1 | `status` | u8 | бит0 — оптический датчик 1, бит1 — датчик 2, бит2 — `mpu_ok`, бит3 — настройки взяты из флеша |
| 2 | `t_ms` | u16 | мс с момента запуска платы, переносится через 65536 мс (≈65.5 с) |
| 4 | `roll` | i16 | °×100, из DMP-кватерниона |
| 6 | `pitch` | i16 | °×100 |
| 8 | `gz` | i16 | сырая угловая скорость по Z, LSB (±2000 °/с → 16.4 LSB/(°/с)) |

`seq` и `t_ms` — то, что отличает «новый отсчёт» от «повтора»: ESP32 может
считать потери (`seq`) и оценивать задержку/джиттер (`t_ms`, метка ставится в
момент отправки кадра).

### 2.2. `DATA_EXT` (0x02), 22 байта payload

Первые 10 байт — как в `DATA`, далее:

| Смещение | Поле | Тип | Смысл |
|---|---|---|---|
| 10 | `yaw` | i16 | °×100 — **без магнитометра дрейфует**, для навигации не годится |
| 12 | `gx` | i16 | сырой гироскоп X |
| 14 | `gy` | i16 | сырой гироскоп Y |
| 16 | `ax` | i16 | сырой акселерометр X (±2 g → 16384 LSB/g) |
| 18 | `ay` | i16 | сырой акселерометр Y |
| 20 | `az` | i16 | сырой акселерометр Z |

Поток идёт либо `DATA`, либо `DATA_EXT` — что включено в `mode`.

## 3. Команды

### `SET_RATE` (0x10), len = 3
`rate_hz` (u16, little-endian) + `save` (u8).

* `rate_hz = 0` — остановить поток (команды и ответы продолжают работать);
* допустимы только делители 200: **1, 2, 4, 5, 8, 10, 20, 25, 40, 50, 100, 200**
  (см. §4); иначе `ACK` с результатом 3;
* `save = 1` — сразу записать настройку во флеш (`ACK` вернёт 4, если запись не
  удалась).

### `SET_MODE` (0x11), len = 1
бит0 — расширенные кадры (`DATA_EXT`), бит1 — светодиоды принадлежат ESP32
(`led_slave`), бит2 — «heartbeat»: при частоте ≤ 5 Гц повторять последний отсчёт
каждые 500 мс, чтобы ESP32 видел, что плата жива. Остальные биты игнорируются.
По умолчанию режим = 0: обычные кадры, светодиоды в локальном режиме.

### `LED` (0x12), len = 2
`mask` (u8, бит0…бит4 = LED1…LED5) + `blink` (u8, период мигания в единицах
100 мс; 0 — постоянно).
Команда действует в любом режиме, но **применяется только при `led_slave = 1`**;
в локальном режиме плата показывает диагностику (§5). Если ESP32 замолчал, плата
**держит последнее состояние** — датчик не должен мигать из-за молчания
контроллера (в отличие от штатной прошивки с её таймаутом 0.6 с).

### `SET_ID` (0x13), len = 1
`id` = 0…15. Нужен, когда плат несколько: ESP32 после включения видит `INFO` и
понимает, какая плата на каком порту.

### `SAVE` (0x14), len = 0
Сохранить текущие параметры (`rate_hz`, `mode`, `id`, `led_mask`).

### `GET_INFO` (0x15), len = 0 → ответ `INFO`

### `INFO` (0xE0), len = 7
`version` (u8, сейчас 1), `id`, `rate_hz` (u16), `mode`, `led_mask`,
`settings_src` (0 — значения по умолчанию, 1 — прочитано из флеша).
Плата сама присылает `INFO` один раз примерно через 0.5 с после включения.

### `ACK` (0xE1), len = 2
`cmd` (type команды) + `result`:

| result | значение |
|---|---|
| 0 | OK |
| 2 | неизвестная команда |
| 3 | недопустимое значение (например, частота, не делящая 200) |
| 4 | ошибка записи во флеш |

Кадры с неверным CRC или длиной **молча отбрасываются** (без `ACK`), чтобы
шумная линия не порождала ответный трафик. Частично принятый кадр сбрасывается
через 20 мс тишины.

## 4. Частоты: почему список именно такой

DMP внутри MPU-6050 всегда работает на 200 Гц, частота потока задаётся
**децимацией** — плата отправляет каждый N-й отсчёт, `N = 200 / rate`:

| rate, Гц | N (каждый N-й отсчёт) | период |
|---|---|---|
| 200 | 1 | 5 мс |
| 100 | 2 | 10 мс |
| 50 | 4 | 20 мс |
| 20 | 10 | 50 мс |
| 10 | 20 | 100 мс |
| 5 | 40 | 200 мс |
| 2 | 100 | 500 мс |
| 1 | 200 | 1 с |

Причина: `dmp_set_fifo_rate(rate)` считает делитель как `200 / rate - 1`
(целочисленно, `Src/mpu6050_dmp.c`), поэтому точны только делители 200.
Выбранный подход «DMP всегда 200 Гц + децимация» ничего не переконфигурирует в
IMU на ходу: смена частоты мгновенная и без «ям» в фильтре DMP.

**Трафик** (200 Гц, кадр 15 B): 3.0 kB/s ≈ 26 % от 115200 8N1 (11.5 kB/s).
`DATA_EXT` (кадр 27 B): 5.4 kB/s ≈ 47 %. Три платы на трёх отдельных UART — это
три независимых канала, 9 kB/s суммарно.

## 5. Светодиоды

* **Локальный режим** (по умолчанию, `led_slave = 0`): LED1 — IMU (ровно =
  `mpu_ok`, мигает ≈2 Гц = ошибка), LED2 — оптический датчик 1, LED3 — датчик 2,
  LED4 — поток включён, LED5 — настройки прочитаны из флеша. Это удобно для
  проверки платы без хоста (заменяет штатное «LED4/LED5 от датчиков»).
* **Режим `led_slave`** (бит1 `SET_MODE`): светодиоды полностью под ESP32 —
  маска и мигание из команды `LED`; состояния не сбрасываются по таймауту.

Все пять выходов — через транзисторы Q7…Q11, питание нагрузки с 15-вольтового
пина (см. `docs/sideboards.md` §5.2): это уровень «реле/оптопара/небольшой
светильник», не «мотор».

## 6. Где хранится конфигурация

Последняя страница флеша — **0x08007C00** (1 КБ; страница GD32F1x0 = 0x400,
подтверждено примером вендорской библиотеки `Examples/FMC/Erase_program`).
Чтобы страница гарантированно не попала под код, в линкер-скрипте
`GD32F130C6T_FLASH.ld` длина FLASH уменьшена с 32K до **31K**.

Структура (16 байт, пишется 4 словами через `fmc_word_program`):

| Смещение | Поле | Смысл |
|---|---|---|
| 0 | `magic` = `0x31534253` | «SBS1» |
| 4 | `version` | 1 |
| 5 | `id` | 0…15 |
| 6 | `mode` | биты режима |
| 7 | — | резерв |
| 8 | `rate_hz` | частота |
| 10 | `led_mask` | маска (чтобы пережить перезапуск) |
| 11 | — | резерв |
| 12 | `crc16` | CRC-16/CCITT-FALSE по первым 12 байтам |
| 14 | — | резерв |

* пишется **только по команде** (`SET_RATE` с `save=1` или `SAVE`) — чтобы не
  изнашивать страницу (ресурс флеша GD32 — десятки тысяч циклов; запись
  происходит на каждый `SAVE`, а не на каждый кадр);
* кадры от хоста разбираются **в прерывании USART IDLE** (`Src/gd32f1x0_it.c` →
  `usart1_rx_check()`), поэтому сама запись во флеш там не делается: команда
  только выставляет флаг, а стирание/программирование выполняет главный цикл
  (`sensor_proto_poll()`), и `ACK` уходит уже после операции. Пока запись идёт
  (≈20–40 мс), новые команды не принимаются — хост повторит по таймауту;
* на время стирания/программирования отключаются прерывания, поток кадров на эти
  миллисекунды «замирает» — ESP32 это переживает по `seq`;
* «полное стирание чипа» программатором (ST-Link Utility: *Erase full chip*)
  сносит настройки → плата вернётся к значениям по умолчанию (200 Гц, id 0);
  *Erase sectors* настройки сохраняет;
* если флеша не хватает, флаг `SBSP_USE_FLASH` в `Inc/config.h` можно убрать:
  тогда конфигурация живёт только в RAM, а ESP32 присылает её после каждого
  включения (протокол тот же, `CMD_SAVE` вернёт результат 4).

## 7. Что нужно на стороне ESP32

* один UART на плату (115200 8N1, RX/TX), питание платы — 12–15 В от DC-DC;
* приёмник — простой автомат состояний: `A5` → `5A` → type → len → payload →
  CRC; при неверном CRC — искать следующий `A5 5A` (не сбрасывать весь буфер);
  на плате этот же автомат живёт в прерывании USART IDLE, у ESP32 его удобно
  держать в задаче чтения UART;
* хранить по плате: `id`, последние `roll`/`pitch`/`gz`, `t_ms`, `seq`, биты
  оптических датчиков; по разнице `seq` считать потери, по `t_ms` — возраст
  отсчёта;
* после старта: дождаться `INFO` (или запросить `GET_INFO`), затем при
  необходимости отправить `SET_ID`, `SET_MODE` (`led_slave`), `SET_RATE`
  и `LED`; на каждую команду ждать `ACK` (таймаут ~10 мс, 2–3 повтора);
* для своих энкодеров/линейки — тот же принцип: «одна сущность = один
  порт/адрес + свой дельта-счётчик/метка времени», плата ничем не отличается.

## 8. Границы и открытые вопросы

* Прошивка **не собиралась** ARM-компилятором в песочнице (тулчейна нет):
  синтаксис проверен `gcc -fsyntax-only` с заглушками, патч — `git apply --check`
  на свежем клоне. Первая сборка — ваша (PlatformIO, `pio run -e VARIANT_SENSOR`).
* **Размер.** Вариант выбрасывает iBUS/AUX и штатные кадры, но добавляет ~1.5 КБ
  протокола и требует держать код ≤ 31 КБ. Если линковщик скажет «region FLASH
  overflowed» — убрать `SBSP_USE_FLASH` и вернуть `LENGTH = 32K` (или сообщить,
  разберёмся, что ещё можно выключить).
* `yaw` из DMP дрейфует (магнитометра нет) — в `DATA_EXT` он есть, но для
  навигации не годится; `roll`/`pitch` — абсолютные, по гравитации.
* Полярность/оси MPU на плате: при первом пуске проверить знаки roll/pitch
  наклоном платы и при необходимости поправить в `MPU_ORIENTATION`
  (`Inc/config.h`).
* DMP отдаёт углы с внутренним фильтром; при 200 Гц фазовая задержка заметно
  меньше, чем при 20 Гц, но всё равно это не сырой гироскоп — если понадобится
  быстрая стабилизация, отдельным шагом добавим поток сырых данных (по той же
  схеме кадров, без DMP).
