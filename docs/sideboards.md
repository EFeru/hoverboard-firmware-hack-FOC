# Боковые платы гироскутера: отладочный режим, сырые данные IMU, светодиоды

Памятка по боковым платам (sideboard / «плата-датчик») и по тому, как использовать
их отдельно от гироскутера: как датчик положения (IMU) и как контроллер
светодиодов.

---

## 1. Коротко: где именно «отладочный режим»

| Вопрос | Ответ |
|---|---|
| Где отладочный режим, о котором пишет вики? | **На боковой плате.** Это вариант `VARIANT_DEBUG` прошивки боковой платы |
| Нужно ли перепрошивать боковую плату? | **Да.** Заводская прошивка общается с основной платой по своему протоколу, и команды/форматы данных из вики в ней отсутствуют |
| А `DEBUG_SERIAL_USART2/3` на основной плате — это то же? | Нет. Это отдельный ASCII-лог величин **основной** платы (входы, батарея, температура). Данных с боковой платы там нет |

Заводская боковая плата передаёт угол на основную плату по **9-битному UART на
~26300 бод**: кадр из 6 девятибитных посылок, первая — признак начала `0x100`,
внутри — знаковое 16-битное значение угла (описано в реверс-проектах, напр.
`OpHaCo/hoverbot`). Прошивка FOC-основной платы такого протокола не понимает —
именно поэтому в вики к `VARIANT_HOVERBOARD` сказано «sideboards need to be
flashed with the hacked version».

## 2. Что есть на боковой плате

| Узел | Детали |
|---|---|
| MCU | GD32F130C6/C8 **или** STM32F103C8 (GD32F103C8) — зависит от партии |
| IMU | MPU-6050 (на I2C0: SCL = PB6, SDA = PB7), 3-осевой гироскоп + 3-осевой акселерометр + DMP |
| Светодиоды | 5 выходов: LED1 = PA0 (красный), LED2 = PB9 (зелёный), LED3 = PB8 (жёлтый), LED4 = PB5 (синий-1), LED5 = PB4 (синий-2); AUX3 (PB10) дублирует LED4 |
| Оптические датчики | 2 фото-прерывателя (PA4 и PC14) — «кнопки»/детектор ноги |
| Связь | 4-пиновый кабель к основной плате: GND, 12/15 В, UART (на боковой плате это USART1 = PA2/PA3, в hack-прошивке 115200) |
| Отладка | SWD-заголовок: GND, 3V3, SWDIO, SWCLK |
| AUX-пины | AUX1..AUX5; AUX4/AUX5 (PA10/PA9) можно использовать как второй UART (USART0) или как I2C (`AUX45_USE_I2C`) |

⚠️ Полярность 4-пинового разъёма у разных партий может быть **обратной**.
Не соединяйте боковую и основную плату из разных партий, не проверив распиновку
(это прямой путь сжечь плату).

### 2.1. Что ещё есть на плате (снято с фото платы)

| Узел | Детали | Практический вывод |
|---|---|---|
| Питание | 12/15 В из кабеля → **78M05** (линейный 5 В) → **AMS1117-3.3** (`U3`) → 3.3 В | на плате есть готовый **5-вольтовый выход** (пин `VDD 5V` на разъёме под RF-модуль) — можно питать внешние датчики, но понемногу (десятки мА, остальное уходит в тепло) |
| Ключи светодиодов | **5 транзисторов `Q7`…`Q11`** (SOT-23) + резисторы 1 кОм (`102`) и 150 Ом (`151`); питание LED-плат — 15 В на разъёмах `J3`/`J4` | 5 независимых **слаботочных** выходов, включённых по низкой стороне (к GND). Годятся для LED, реле, оптопар, MOSFET-модулей; напрямую мотор не потянут |
| Оптические датчики | 2 фото-прерывателя: `PA4` (SENSOR1), `PC14` (SENSOR2) | готовые «кнопки»/концевики/метки на валу без внешних деталей |
| `AUX1_PU` | `PC15` — вход с подтяжкой | «сухой» вход под кнопку или 1-проводный датчик |
| Батарейка | `U1` = **SGM4054** (зарядник Li-ion) + литиевая банка | судя по обвязке — питание домена BKP/RTC; как автономное питание платы не рассчитано (проверять) |
| RF-модуль | `HFY-J18` (UART), у большинства плат **не распаян** | на части партий вместо него стоит Bluetooth-модуль |
| Прошивка/отладка | SWD: `GND`, `3V3`, `SWDIO` (PA13), `SWCLK` (PA14) | прошивка только через SWD — другого пути нет |

**Главный вывод:** боковая плата — это не «датчик», а готовый узел ввода-вывода:
IMU + 2 оптических входа + 5 выходных ключей + стабилизаторы (12/15 В → 5 В → 3.3 В)
в одном корпусе.

### 2.2. CAN и DroneCAN

Про CAN-трансивер, DroneCAN (свет и «просто управляемые выводы»), сырьё IMU по
шине и про подключение платы к ArduPilot/PX4/ROS2 через ESP32 — отдельный
документ: [`docs/can-dronecan-sideboard.md`](can-dronecan-sideboard.md).
Коротко: **у STM32F103C8T6 CAN есть** (PA11/PA12), **у GD32F130C6T6 — нет**. Для
подключения к гироскутеру верна общая оговорка из §7 ниже — совместимость с
прошивкой основной платы не требуется вовсе.

### 2.3. Как связывать плату с ESP32/Arduino и чем

Разбор «свой протокол или MAVLink» для пары «боковая плата ↔ ESP32» с готовыми
кадрами, таймингами и размерами MAVLink-сообщений:
[`docs/sideboard-esp32-protocol.md`](sideboard-esp32-protocol.md).

Реализация этого решения — вариант прошивки `VARIANT_SENSOR` (протокол **SBSP v1**):
плата отдаёт roll/pitch, gyro Z, состояние оптических датчиков, принимает команды
светодиодов и умеет менять частоту 1…200 Гц с сохранением в свою флеш-страницу.
Спецификация и готовые файлы/патч: [`docs/sideboard-sensor/`](sideboard-sensor/PROTOCOL.md).

## 4. Отладочный режим (`VARIANT_DEBUG`): как прочитать сырые данные

### 4.1. Подготовка

1. Скачать репозиторий под свой чип (см. таблицу выше), открыть папку в VS Code.
2. Собрать вариант DEBUG: `pio run -e VARIANT_DEBUG` (или кнопка Build после
   выбора окружения в `Project Tasks`).
3. Прошить боковую плату через ST-Link (см. §6) — файл `firmware.bin`
   по адресу `0x08000000` (ST-Link Utility / STM32CubeProgrammer).
4. Подключить USB-UART адаптер **3.3 В** к кабелю платы: `TX платы → RX адаптера`,
   `GND ↔ GND`. **Красный провод (12/15 В) не подключать!**
5. Открыть монитор порта на **115200** бод.

### 4.2. Команды

При старте плата сама печатает подсказку (как `h`). Полный список:

| Команда | Действие |
|---|---|
| `h` | Печать справки |
| `a` | Вкл/выкл печать **акселерометра** (сырые данные) |
| `g` | Вкл/выкл печать **гироскопа** (сырые данные) |
| `q` | Вкл/выкл печать **кватерниона** (DMP) |
| `e` | Вкл/выкл печать **углов Эйлера** (deg × 100) |
| `t` | Вкл/выкл печать **температуры** (°C × 100) |
| `p` / `0` | Шагомер вкл/выкл / сброс шагомера |
| `1` / `2` / `3` | Частота DMP/MPU: 10 / 50 / 100 Гц |
| `f` / `v` | DMP вкл/выкл / кватернионы вкл/выкл |
| `8` / `9` | Акселерометр вкл/выкл / гироскоп вкл/выкл |
| `r` | Дамп регистров MPU-6050 (отладка I2C) |
| `s` | Запуск self-test (плата должна лежать строго горизонтально) |
| `w` | Тест low-power режима акселерометра |
| `,` / `.` | Прерывание DMP: по жесту / периодическое |
| `x` | Печать данных второго (AUX) UART |

### 4.3. Формат строк (пример)

```
accX:1234 accY:-567 accZ:16384
gyrX:12 gyrY:-8 gyrZ:3
qW:10737 qX:0 qY:-5 qZ:1
Roll:12 Pitch:-345 Yaw:87
Temp:2431
```

* Углы Эйлера — в **градусах × 100** (`Pitch:-345` → −3.45°).
* Температура — в **°C × 100**.
* Акселерометр при ±2g даёт ~16384 LSB на 1g (в покое по оси Z ≈ 16000).
* Гироскоп настроен на ±2000 °/с (требование DMP), ~16.4 LSB на °/с.
* Данные печатаются раз в 50 мс главного цикла (≈20 Гц) — частота задаётся
  `MPU_DEFAULT_HZ` в `Inc/config.h` и командами `1`/`2`/`3`.

### 4.4. Полезные «побочные» индикаторы в этом варианте

* Фото-датчик 1 сработал → включается LED4 (синий) и печатается `SENSOR 1 ON/OFF`;
  датчик 2 → LED5.
* IMU не отвечает → мигает красный LED1; таймаут AUX → мигает жёлтый LED3.
* При старте выполняется короткое световое «демо» (`intro_demo_led`).

### 4.5. Готовое демо 3D-визуализации

В репозитории есть скетч Processing (`docs/sketch_processing/`), который строит
3D-модель по кватернионам — удобно, чтобы сразу увидеть, что датчик живой.

## 5. Использование платы как датчика и как «контроллера света»

### 5.1. Как датчик положения
Два практичных пути:

1. **`VARIANT_DEBUG` + разбор ASCII-строк** — проще всего для экспериментов: своя
   плата (Arduino/ESP32) читает строки `Roll:... Pitch:... Yaw:...` и парсит их.
   Минус — «текстовый» протокол, медленнее и без контроля целостности.
2. **`VARIANT_HOVERBOARD` + бинарный протокол** — оптимально для робота. Боковая
   плата сама ~каждые 5 мс (≈200 Гц, `main_loop_counter % 5` при цикле 1 мс)
   отправляет пакет `SerialSideboard` (14 байт, все поля 16-битные — паддинга нет):

   | Смещение | Поле | Смысл |
   |---|---|---|
   | 0 | `start` | всегда `0xABCD` |
   | 2 | `pitch` | угол (из углов Эйлера), deg × 100 |
   | 4 | `dPitch` | производная угла (гироскоп по Y) |
   | 6 | `cmd1`, `cmd2` | каналы с AUX-приёмника (iBUS), 0 если не подключён |
   | 10 | `sensors` | маска: бит0 — фото-датчик 1, бит1 — фото-датчик 2, бит2 — `1` = IMU исправен, биты 8..15 — переключатели RC (каналы 7..10) |
   | 12 | `checksum` | XOR всех предыдущих полей |

   Ваша плата-хозяин принимает 14-байтовые пакеты, ищет заголовок `0xABCD`,
   проверяет XOR — и получает готовый угол без возни с I2C и DMP.

### 5.2. Как «контроллер света»

Светодиодами управляет сама боковая плата: у неё 5 GPIO-выходов (LED1..LED5,
см. §2), к которым подключаются LED-платы гироскутера.

* В `VARIANT_HOVERBOARD` она принимает от основной платы пакет `SerialFeedback`
  и берёт из него готовую маску светодиодов (поле `cmdLed`):

  | Бит | Значение | Что показывает в штатной логике |
  |---|---|---|
  | `0x01` | LED1 (красный) | критическая ошибка / низкий заряд |
  | `0x02` | LED2 (зелёный) | норма (уровень батареи) |
  | `0x04` | LED3 (жёлтый) | предупреждение |
  | `0x08` | LED4 (синий-1) | «моторы разрешены» (+ дублируется на AUX3) |
  | `0x10` | LED5 (синий-2) | задний ход / торможение |

  Достаточно слать по UART свою 18-байтовую структуру с нужной маской — и все
  светодиоды под вашим контролем (готовый код кадра, формула XOR и условие по
  длине посылки — в [`docs/sideboard-esp32-protocol.md`](sideboard-esp32-protocol.md) §3.3–3.4).
  ⚠️ Учтите: если пакеты перестанут приходить,
  плата перестаёт обновлять светодиоды и начинает мигать жёлтым (таймаут).

* Ещё проще: если светодиоды нужны без IMU — можно собрать свою мини-прошивку на
  базе sideboard-hack, где команды вида «включить LED2», «выключить LED3»
  принимаются по одному байту. Основа уже есть: `handle_leds()` в `Src/util.c`.

**Реальные пределы выходов.** Каждый LED-канал — это не «прямая ножка МК», а
отдельный транзистор (`Q7`…`Q11`), включённый по низкой стороне, с базовым
резистором 1 кОм. Практический потолок такого канала — единицы десятков /
первые сотни миллиампер при напряжении до 15 В. Это уровень «реле, оптопара,
небольшой светильник», а не «мотор». Чтобы управлять средней нагрузкой,
ключ боковой платы включает **внешнее реле или MOSFET-модуль** — а тот уже
коммутирует нагрузку. Плюс: 5-вольтовый выход на плате позволяет питать
небольшую внешнюю логику.

### 5.3. Несколько плат сразу

У каждой боковой платы свой UART, общей шины нет: на каждую плату нужен отдельный
порт вашего контроллера. Если плат много, а нужны только светодиоды — дешевле
взять одну плату и развести LED-выходы; либо использовать AUX-пины
(`AUX45_USE_I2C`) для связи по I2C между платами.

## 6. Прошивка боковой платы: пошагово

1. **Определить чип** по маркировке на корпусе → выбрать репозиторий (§3).
2. Подключить ST-Link V2 к SWD-заголовку: `GND`, `SWDIO`, `SWCLK`
   (и `3V3`, если плата не питается от 12/15 В).
3. **Снять защиту**. Заводская плата залочена: в ST-Link Utility будет
   «Can not read memory!». `Target → Option Bytes → Read Out Protection = Disable`
   → `Apply`; либо OpenOCD:
   ```
   openocd -f interface/stlink.cfg -f target/stm32f1x.cfg -c init -c "reset halt" -c "stm32f1x unlock 0"
   ```
   ⚠️ **Необратимо.** Заводскую прошивку сохранить нельзя — она стирается.
   Если плата выключается во время операции, держите кнопку питания.
4. Собрать: `pio run -e VARIANT_DEBUG` (или `VARIANT_HOVERBOARD`).
   Либо взять `firmware.bin` из артефакта GitHub Actions (в GD-репозитории есть
   готовый workflow).
5. Прошить `firmware.bin` (адрес `0x08000000`) через ST-Link Utility или
   STM32CubeProgrammer.
6. Если после прошивки поведение странное — повторить разблокировку с
   «галочками» в `User configuration option bytes` (см. Troubleshooting в вики
   «How to Unlock MCU Flash»).

## 7. ⚠️ Совместимость с нашей прошивкой основной платы

Прошивка FOC-основной платы **умеет** работать с боковыми платами — макросами
`SIDEBOARD_SERIAL_USART2/3` (приём угла и датчиков) и
`FEEDBACK_SERIAL_USART2/3` (передача маски света). В нашей боевой сборке
(`VARIANT_LUART_RPWM`: левый кабель = UART для Arduino, правый = PWM) они
выключены, поэтому боковые платы сейчас не задействованы.

Если включать — важны **длины пакетов**:

| Направление | Наша прошивка | Прошивка боковой платы | Итог |
|---|---|---|---|
| Боковая → основная (`SerialSideboard`) | 14 байт | 14 байт | ✔ совпадает |
| Основная → боковая (`SerialFeedback`) | **32 байта** | **18 байт** | ✘ не совпадает |

Почему 32: `start, cmd1, wheelR_cnt (int32), wheelL_cnt (int32), cmd2,
speedR_meas, speedL_meas, left_dc_curr, right_dc_curr, batVoltage, boardTemp,
cmdLed, reserved, checksum`.

Почему это критично: боковая плата принимает данные **строго по длине**
(`Feedback_len = sizeof(Feedback)` = 18) и проверяет XOR. Пакет из 32 байт она
не распознает → поле `cmdLed` не обновляется → по таймауту `timeoutFlagSerial1`
она перестаёт управлять светодиодами и мигает жёлтым (`LED3`).

Причём это касается и апстрима: в `EFeru/hoverboard-firmware-hack-FOC`
(`Src/main.c`, структура под `FEEDBACK_SERIAL_USART2/3`) по умолчанию кадр
ровно **18 байт** и с боковой платой совпадает, но стоит включить
`ENABLE_ODOMETRY` (в `Inc/config.h` он есть и по умолчанию закомментирован) —
и в кадре появятся счётчики `wheelR_cnt`/`wheelL_cnt` (в апстриме — `int16_t`),
кадр станет 22 байта и со штатной боковой платой перестанет совпадать. Полей
`left_dc_curr`/`right_dc_curr` в апстримном кадре нет вовсе — они добавлены
в нашей сборке. То есть пара «основная + боковая» работает только при точном
совпадении структур, и наш 32-байтовый кадр (int32-счётчики + DC-токи +
`reserved`) без патча одной из сторон не стыкуется ни с боковой платой, ни
с апстримным кадром.

Что можно сделать (по запросу):

* **патч прошивки боковой платы** — привести `SerialFeedback` к нашим 32 байтам
  (поля в том же порядке + XOR по нашим полям), тогда индикация батареи и
  светодиоды снова управляются с основной платы;
* **отдельное окружение в прошивке основной платы** — «только чтение боковой
  платы» (углы/датчики без моторов), удобно для стенда;
* **своя мини-прошивка боковой платы** — поток углов + простые команды света
  (разбор вариантов и готовые кадры — в `docs/sideboard-esp32-protocol.md`).

## 8. Разные IMU на разных партиях

| IMU | Сырые акселерометр/гироскоп | DMP (кватернионы, углы Эйлера) | Примечание |
|---|---|---|---|
| MPU-6050 / MPU-6050C / MPU-6052C | ✔ | ✔ | полная поддержка |
| MPU-6050A | ✔ | ❌ | на самом деле **ICM-20689**; сырые данные работают, если отключить DMP в `config.h` |
| ICM-20618, ICM-20630, ICM-20681, BNO055 | ❓ | ❓ | поддержка не подтверждена — проверяйте командами `a`/`g`/`e` |

Как проверить свою плату: в отладочном режиме нажать `a`, `g`, `e` — если в
строках появляются ненулевые значения, соответствующая функция поддерживается.

## 9. Разбор частых вопросов

### 9.1. `VARIANT_DEBUG` и `VARIANT_HOVERBOARD` — это не режимы, а разные сборки

Вариант выбирается **один на всю прошивку** и вшивается на этапе компиляции:

* в `platformio.ini` раскомментирована строка `default_envs = VARIANT_DEBUG`
  (или собираете `pio run -e VARIANT_HOVERBOARD`, или правите `Inc/config.h`).

Переключить вариант «на ходу», командой по UART, **нельзя** — плату надо
перепрошить. Сборки отличаются тем, чем занят главный UART:

| Вариант | Главный UART (кабель к основной плате) | Для чего |
|---|---|---|
| `VARIANT_DEBUG` | человек с USB-UART | смотреть данные и подавать команды |
| `VARIANT_HOVERCAR` | основная плата (углы + RC) | канал управления из iBUS + свет |
| `VARIANT_HOVERBOARD` | основная плата (протокол FOC) | штатная работа в паре с FOC-платой |

То есть для «посмотреть сырые данные» — собираете и прошиваете `VARIANT_DEBUG`;
для работы с основной платой — заливаете `VARIANT_HOVERBOARD` (это уже другая
прошивка).

### 9.2. Биты 8–15 в `sensors`: откуда там RC-переключатели

Это результат **iBUS-приёмника**, подключённого к AUX-пинам боковой платы
(AUX4 = PA10 — приём, AUX5 = PA9 — передача, 115200 бод). Приёмник шлёт по
одному проводу цифровые посылки (32 байта: `0x20 0x40`, 14 каналов по 2 байта,
контрольная сумма), плата раскладывает их на каналы.

Из каналов берётся:

| Бит в `sensors` | Источник | Имя в прошивке основной платы | Смысл |
|---|---|---|---|
| 0 | фото-датчик 1 | `SENSOR1_SET` | «кнопка» / нога на платформе |
| 1 | фото-датчик 2 | `SENSOR2_SET` | то же |
| 2 | — | — | `1` = IMU исправен |
| 8 | канал 7 RC | `SWA_SET` (0x0100) | переключить управление на боковую плату |
| 9–10 | канал 8 RC (3 позиции) | `SWB_SET` (0x0600) | тип управления (Control Type) |
| 11–12 | канал 9 RC (3 позиции) | `SWC_SET` (0x1800) | режим управления (Control Mode) |
| 13 | канал 10 RC | `SWD_SET` (0x2000) | вкл/выкл Field Weakening |

Если приёмник не подключён, все эти биты просто нули (а по таймауту AUX
`cmd1`/`cmd2` обнуляются).

**PWM боковая плата не читает.** Каналы приходят только цифровым протоколом
**iBUS** (FlySky/Turnigy-совместимые приёмники), никаких импульсов 1000–2000 мкс
на входе нет. Если у вас приёмник с PWM/PPM/SBUS — его к боковой плате напрямую
не подключить (PWM-вход есть только у основной платы, `CONTROL_PWM_LEFT/RIGHT`).

### 9.3. Что такое I2C и что такое DMP

**I2C** — двухпроводная шина, по которой микроконтроллер боковой платы общается
с микросхемой IMU **внутри самой боковой платы** (SCL = PB6, SDA = PB7, скорость
400 кГц). Наружу эти провода не выходят: вы просто читаете результат по UART.
Отдельно: пины AUX4/AUX5 можно переключить в режим I2C (`AUX45_USE_I2C`), чтобы
подцепить к боковой плате внешнее устройство; и в основной плате правый кабель
тоже умеет I2C (джойстик/дисплей). Команда `r` в отладочном режиме как раз
проверяет эту шину — дампит регистры IMU.

**DMP** (Digital Motion Processor) — маленький вычислитель **внутри** микросхемы
MPU-6050. При старте прошивка закачивает в IMU бинарный «блоб»
(`Src/mpu6050_dmp.c`), и дальше IMU **сам** считает кватернионы, углы Эйлера и
шаги, складывая результат в свои регистры. Микроконтроллер только читает готовые
числа — отсюда команды `q` (кватернион), `e` (углы), `t`, `p` (шагомер).

* DMP включён → готовые углы, но обязательны жёсткие настройки: гироскоп
  ±2000 °/с, акселерометр ±2 g, частота 10/50/100 Гц.
* DMP выключен (`MPU_DMP_ENABLE` закомментирован) → микроконтроллер читает
  «сырые» регистры: `a` (ускорения), `g` (угловые скорости), а углы считаете сами
  (интегрирование гироскопа). Именно этот режим нужен для MPU-6050A.
* Именно поэтому в вики для MPU6050A отмечено, что сырые данные через `a`/`g`
  доступны только при выключенном DMP: не потому что «сырые данные сложнее»,
  а потому что на этой микросхеме (по факту ICM-20689) блоб от InvenSense
  не работает.

### 9.4. Куда физически включается боковая плата

Боковая плата **не подключается параллельно** чему-либо. У неё один 4-жильный
кабель (GND, 12/15 В, UART), и он вставляется **в тот же самый разъём основной
платы**, в который иначе вставляется кабель управления (слева — USART2, справа —
USART3). То есть один разъём = одна роль:

```
Основная плата                     Что в разъёме слева (USART2)
─────────────────                  ────────────────────────────
разъём ← 4-жильный кабель →  ┌── кабель к Arduino/драйверу (CONTROL_SERIAL_USART2)
                             └── ИЛИ боковая плата           (SIDEBOARD_SERIAL_USART2)
```

Прошивка это прямо запрещает — в `Inc/config.h`:

```c
#if defined(CONTROL_SERIAL_USART2) && defined(SIDEBOARD_SERIAL_USART2)
  #error CONTROL_SERIAL_USART2 and SIDEBOARD_SERIAL_USART2 not allowed, choose one.
#endif
```

Обмен по этому кабелю идёт в **две стороны**:

* боковая → основная: 14-байтовый `SerialSideboard` (угол `pitch`, `dPitch`,
  каналы RC, датчики) — основная плата берёт угол и датчики;
* основная → боковая: `SerialFeedback` (скорости, напряжение, температура,
  `cmdLed`) — боковая плата зажигает светодиоды по маске `cmdLed`.

Вот почему «формат должен совпадать»: это двусторонний обмен структурами по
одному проводу, и обе стороны должны понимать одинаковые структуры. Если длины
не совпадают, боковая плата просто не находит свой пакет и переходит в таймаут
(жёлтое мигание), а светодиоды перестают управляться.

**Для вашего сценария это неважно:** если боковая плата работает сама по себе
(со своей платой-хозяином на другом конце кабеля), совместимость с прошивкой
основной платы вообще не нужна — вы просто читаете её UART в удобном для вас
формате.

## 10. Что стоит запомнить


* «Отладка» — на **боковой** плате, нужна перепрошивка (`VARIANT_DEBUG`).
* Сырые данные: команды `a` (акселерометр), `g` (гироскоп), `q` (кватернион),
  `e` (углы), `t` (температура), порт 115200.
* Для робота удобнее бинарный протокол `VARIANT_HOVERBOARD` (14-байтовые пакеты
  с `0xABCD` и XOR).
* Светодиоды — 5 обычных GPIO, управляются битовой маской; годится и для
  отдельного «умного света».
* Разблокировка чипа необратима, 5 В в UART нельзя, 12/15 В из кабеля — только
  на питание платы, платы из разных партий не смешивать без проверки распиновки.
