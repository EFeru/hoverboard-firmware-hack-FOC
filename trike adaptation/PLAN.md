# План работ — TRIKE adaptation

> **Архитектура разработки:** upstream EFeru `main` — неизменяемая исходная база, из которой берутся необходимые алгоритмы и инфраструктура. Рабочая ветвь проекта — `trike-adaptation`; все изменения адаптации выполняются только в `trike adaptation/`. Вариант HOVERCAR — донор исходной логики и пример реализации, а не главная ветвь форка и не готовая конфигурация TRIKE. Не смешивать upstream, HOVERCAR и собственные изменения TRIKE.

> **Приоритет требований:** согласованные пользователем требования и таблица процедур TRIKE имеют приоритет над унаследованным поведением EFeru/HOVERCAR. Несовпадающие обработчики не наслаивать друг на друга: их требуется заменить или адаптировать. FOC, силовая архитектура, измерения и штатные защиты сохраняются, если отдельным анализом не доказана необходимость изменения.

> **Статусы:** раздел 0 фиксирует согласованные требования, а не факт их реализации. Галочка в разделах требований означает «согласовано». В этапах реализации галочка означает только выполненную работу по исходникам/документации; аппаратная проверка отмечается отдельно. Не считать функцию готовой к эксплуатации до сборки и соответствующих испытаний.


## 0. Зафиксированные требования (не менять без отдельного решения)

### Аппаратная конфигурация
- [x] Одна зелёная плата hoverboard, MCU STM32F103RCT6.
- [x] Использовать два штатных FOC-канала одной платы.
- [x] Два задних мотор-колеса 350 Вт — по одному на каждый канал.
- [x] Независимая подвеска задних колёс.
- [x] Диаметр колёс по исходному проектному заданию — 8".
- [x] Механическая ориентация моторов требует правильной противоположной полярности каналов. EFeru уже задаёт штатные разные знаки для LEFT/RIGHT; дополнительный `INVERT_*` флаг пока не выбран и будет включён только после проверки на стенде.
- [x] Не объединять каналы, фазы, MOSFET или токовые измерения. Никакого «одного мотора на 12 MOSFET».

### Поведение
- [x] Одна трёхпроводная Hall-ручка газа.
- [x] Газ синхронно задаёт тягу обоим моторам.
- [x] Питание Hall-ручки 5 В по умолчанию; 3,3 В не использовать как штатное питание.
- [x] Передний тормоз — цифровой сигнал.
- [x] При торможении — управляемая нарастающая рекуперация задними мотор-колёсами.
- [x] Газ отпущен — свободный выбег, без автоматической рекуперации.
- [x] Заднего тормоза нет.
- [x] Пользовательского реверса транспорта нет.
- [x] Сохранить полноценный аварийный режим и штатные защиты.
- [x] Радио/Bluetooth, UART-команды, дисплей и боковые платы не нужны.
- [x] Цель по скорости — 27–30 км/ч.

### Параметры, обсуждавшиеся как целевые
- Плавное нарастание рекуперации: около 1 с.
- Снятие рекуперации: около 0,5 с.
- Предусмотреть стартовый выбор M1/M2/M3.
- Ограничения скорости и тока должны быть отдельными параметрами конфигурации.
- Упоминался запас порядка +2 А, но окончательные значения токовых лимитов не утверждены. Не подставлять произвольные значения.

### Пользовательские процедуры — обязательная спецификация

Точная последовательность действий пользователя вынесена в отдельный документ [STARTUP_PROCEDURES_RU.md](STARTUP_PROCEDURES_RU.md). Этот документ является нормативным источником для обработчиков кнопки питания, выбора режимов и калибровки. Не заменять его унаследованными комбинациями HOVERCAR или стандартными процедурами EFeru.

Согласованные процедуры:
- Обычный запуск: удержание кнопки питания 2 секунды без предварительных коротких нажатий; запуск в последнем сохранённом режиме.
- Выбор M1/M2/M3: соответственно 1/2/3 коротких нажатия, затем отдельное нажатие с удержанием 2 секунды.
- Если сохранённого режима нет — обычный запуск использует M1.
- Режим сохраняется только после распознавания корректной команды.
- Некорректная или незавершённая последовательность отменяет запуск; нельзя автоматически трактовать её как обычное включение или переключать на другой режим.
- Первичная фиксация нуля: при первом включении отпущенная и стабильная ручка задаёт `THROTTLE_ZERO`, который сохраняется во Flash; нажатый или нестабильный газ отменяет запуск без записи.
- Полная калибровка: полностью нажатый газ + кнопка питания, удержание 5 секунд; сохранение диапазона — только после успешной проверки.

**Не реализовано:** обработчики этих процедур, временные окна коротких нажатий, параметры M1/M2/M3 и хранение/проверка соответствующих данных во Flash. Точные временные окна коротких нажатий должны быть определены в конфигурации и проверены испытаниями.

## 1. Что уже проверено по исходному коду

### 1.1 HOVERCAR как исходная точка
В `Inc/config.h` вариант HOVERCAR сейчас:
- использует `CONTROL_ADC`;
- ожидает два аналоговых педальных входа;
- включает `DUAL_INPUTS`;
- подключает `SIDEBOARD_SERIAL_USART3` и `FEEDBACK_SERIAL_USART3`;
- содержит логику `MULTI_MODE_DRIVE`;
- содержит настройки направления каждого мотора;
- содержит опциональные круиз-контроль, удержание и электрическое торможение.

В `Src/main.c` для HOVERCAR присутствуют:
- двойное нажатие тормоза для распознавания реверса;
- взаимное подавление педали газа при нажатии тормоза;
- преобразование тормозной педали в отрицательную команду;
- объединение команд для движения вперёд/назад;
- общий фильтр/ограничитель скорости изменения команды;
- установка отдельных `pwmr` и `pwml`.

Для TRIKE это не подходит напрямую: входная модель меняется с двух педалей на один Hall-газ плюс отдельный цифровой тормоз. HOVERCAR остаётся донором архитектуры и фильтрации, но не готовой конфигурацией.

### 1.2 Два независимых моторных канала
В исходниках присутствуют отдельные структуры параметров и результаты контроллеров:
- `rtP_Left`, `rtY_Left`;
- `rtP_Right`, `rtY_Right`;
- отдельные команды `pwml`, `pwmr`;
- отдельные TIM1/TIM8, ADC-измерения, Hall-входы и токовые сигналы.

В схеме на странице 1 это соответствует двум самостоятельным трёхфазным мостам и раздельным цепям измерения тока. Сохраняем эту архитектуру без объединения силовых частей.

### 1.3 Важное ограничение по Hall-газу
Наличие 5-вольтовой линии на схеме не означает, что любой сигнал с ручки можно напрямую подавать на ADC STM32. Питание датчика и диапазон его сигнального выхода — разные электрические цепи. Перед фиксацией ADC-входа нужно измерить сигнал ручки по всему ходу и проверить конкретный разъём/делитель/защиту входа.

## 3. Что пока НЕ зафиксировано

Эти пункты нельзя подменять догадками:
1. Подтверждение PA3/UART_L_RXD, PB11/UART_R_RXD и полярности на конкретной ревизии зелёной платы.
2. Фактический диапазон сигнала ручки после делителя и окончательные номиналы согласователя.
3. Фактическая точка 5 В на конкретной ревизии зелёной платы и её допустимый ток; UART-разъёмы выдают +VSW, не +5 В.
4. Какой из двух каналов должен получить `INVERT_*_DIRECTION` после физического теста.
5. Реальная окружность нагруженного 8-дюймового колеса и соответствие оборотов двигателя скорости; сейчас используется расчётный диаметр 203 мм.
6. Окончательные токовые лимиты, температурные пороги и параметры рекуперации.
7. Длительность отдельного короткого нажатия и точное правило отсчёта общего окна ввода 2000 мс; необходимость отдельных ограничений скорости/ускорения для M1/M2/M3.
8. Стендовая проверка независимого отключения каналов. В исходном EFeru общий флаг отключал оба мотора; в TRIKE добавлена отдельная защёлка на канал после анализа диагностических битов.
